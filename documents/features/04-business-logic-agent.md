# ビジネスロジック・ユースケース個別解析エージェント 機能仕様書

Issue #34（親 Issue #17 / STEP 2-④）の機能仕様。

## 1. この機能で解決すること

引き継いだレガシーシステムにおいて、仕様書が存在しないか、あるいは現在のコードと大きく乖離している場合、業務フローや状態遷移の仕組みを正確に把握することは極めて困難である。
本エージェントは、ソースコード内のビジネスロジック（サービス層、ドメインモデル、ユースケース定義など）を専門に解析し、**主要なビジネスフローの言語化、状態遷移のトリガーと遷移先特定、および主要機能一覧**を抽出して、ビジネスロジック・ユースケース仕様書（`business_logic_spec.md`）を自動生成する。

基本方針はリポジトリ全体の思想と揃える。

- アプリケーションコードを「正」として扱う。
- 根拠（ファイルパス）を示せない内容は断定しない。
- 抽出できない箇所は「判断不能」として明示する。

## 2. 位置づけ

`apps/analysis-worker` の解析パイプラインに組み込まれる個別エージェント。
他の解析処理（F-02, F-03 など）と並行し、ビジネスロジックに特化した成果物を 1 つ追加する。

- 実装: `apps/analysis-worker/src/business-logic.ts`
- オーケストレータ: `apps/analysis-worker/src/orchestrator.ts` の `businessLogicAgent`
- 成果物: `business_logic_spec.md`

## 3. 入力仕様

解析対象のソースコード群に含まれる、主要なビジネスロジックを含むコードファイルを自動判別して解析する。

### 判定・抽出条件

| 種別 | 判定条件 |
| --- | --- |
| 解析対象のプログラミング言語 | 拡張子: `.js` / `.ts` / `.jsx` / `.tsx` / `.py` / `.go` / `.java` / `.rb` / `.php` / `.cs` / `.cpp` / `.c` |
| 除外条件 | テストファイル、IaC ファイル（`.tf`等）、`.gitignore` などの設定ファイル、README、ドキュメント、および `node_modules` / `dist` などのビルド成果物 |

非ビジネスロジックファイル（設定、インフラ定義、テストコード等）はプロンプトのコンテキストを節約するため極力除外し、アプリケーション実装の本質的なロジックのみを抽出してエージェントに渡す。

## 4. 処理の流れ

1. アプリケーションコード全体からビジネスロジック候補ファイルを抽出する（`filterBusinessLogicFiles`）。
2. 各ファイルに対して軽量な静的構造抽出を行う（`buildBusinessLogicOverview`）。
   - クラス定義、関数定義、インターフェース定義などの主要シンボルを正規表現ベースで簡易抽出する。
   - サマリー情報（総ファイル数、総行数、総文字数）を算出する。
3. 静的抽出結果を Markdown サマリーに整形する（`renderBusinessLogicOverviewMarkdown`）。
4. サマリーとビジネスロジック入力本文を `[TASK: BUSINESS_LOGIC_SPEC]` プロンプトに組み立てる（`buildBusinessLogicSpecPrompt`）。
5. Gemini API で意味的な仕様書を生成し、静的サマリーと結合して `business_logic_spec.md` を出力する。
   - ビジネスロジック候補ファイルが 0 件の場合は Gemini API を呼び出さず、抽出不能であることを明示したフォールバック成果物を出力する。

## 5. 出力仕様（business_logic_spec.md）

Gemini への出力指示として、次の章立てを推奨する。

1. システム主要機能一覧（機能名、概要、関係するソースファイル、エンドポイント等の関連情報）
2. 主要なビジネスフローの定義（データフロー、登録/更新などのメインフロー）
3. 状態遷移とトリガー（ステータス変数の定義、遷移条件、イベント/トリガー、遷移先）
4. 業務ルール・バリデーション規則（バリデーション項目、制約条件、エラー時の挙動）
5. 判断不能・推測事項（仕様が不明瞭な箇所やコードから確定できなかったロジック）

成果物の冒頭には、静的解析結果（解析対象ファイル一覧、主要シンボル一覧）を併記し、Gemini の生成内容が静的事実と突き合わせて検証できるようにする。

## 6. MVPではやらないこと

- 言語ごとの詳細なデータフロー解析や依存関係の完全なグラフ解析（静的解析の中間成果物や Gemini の推論に委ね、ワーカー自体には重厚な AST パーサーは組み込まない）。
- 外部連携先システムの挙動シミュレーション。

## 7. テスト

`apps/analysis-worker/test/business-logic.test.ts` で以下を検証する：
- アプリケーションコードのフィルタリング処理。
- JS/TS, Python, Go 等の言語におけるクラス・関数・構造体定義などの静的シンボル抽出。
- プロンプト組み立て処理。
- エージェント結合テスト（Gemini クライアントはスタブを使用）。
