# ハーネスエンジニアリング運用規約（git-agent 思想）

本リポジトリは「**git-agent 思想**」に基づき、AI エージェントの作業環境（ハーネス）そのものを
git 管理対象として育てます。本ドキュメントはその考え方と運用ルールを定めます。

## 1. なぜハーネスを git 管理するのか

PhoenixDevOps が解決しようとしている課題は「ドキュメントと実態の乖離」「IaC の崩壊」です。
これは裏を返せば、**暗黙知・属人的な手順・コンソール手動操作が積み重なるとシステムは壊れる**
という教訓そのものです。

同じ失敗を自分たちの開発プロセスで繰り返さないために、エージェントの動かし方（コンテキスト・
権限・定型作業・レビュー観点）をすべて明文化し、コードと同じ土俵（git / PR / レビュー）に載せます。
これにより、

- 誰がどのエージェント／ツールを使っても **同じ前提・同じ規約** で動く
- ハーネスの改善が **diff として可視化・レビュー・巻き戻し** できる
- 新メンバー（人間も AI も）が **リポジトリを clone するだけで即戦力化** できる

## 2. ハーネスの構成要素

| 要素 | 場所 | 役割 |
| --- | --- | --- |
| プロジェクト憲法 | [CLAUDE.md](../../CLAUDE.md) | アーキテクチャ・規約・禁止事項。全エージェントが起動時に読む正本 |
| 他ツール入口 | [AGENTS.md](../../AGENTS.md) | Claude 以外のツール向け要点（正本は CLAUDE.md） |
| 共有設定 | `.claude/settings.json` | チーム共有の権限（allow / ask / deny）。破壊的操作は deny/ask |
| 個人設定 | `.claude/settings.local.json` | 各自のローカル設定。**git 管理しない**（.gitignore 済み） |
| カスタムコマンド | `.claude/commands/*.md` | 定型作業の手順化（`/spec` `/tf-plan` `/issue-branch`） |
| サブエージェント | `.claude/agents/*.md` | 専門レビュー（`iac-reviewer` `spec-guardian`） |
| 規約ドキュメント | `documents/engineering/` | 本ファイルなど、運用の明文化 |

## 3. 運用ルール

### 3.1. ハーネスもレビュー対象
`.claude/` 配下や CLAUDE.md / AGENTS.md の変更も、コードと同様に PR でレビューする。
「エージェントの振る舞いを変える」変更は影響範囲が広いため、独立した PR にすることを推奨する。

### 3.2. 権限は最小から
`.claude/settings.json` の `allow` は、読み取り・検証系（`gh issue` / `terraform validate` 等）に限定する。
状態を変える操作（`git push` / `terraform apply`）は `ask`、破壊操作（`terraform destroy` / 各種 delete）は
`deny`。権限を広げたいときは PR で理由を添えて提案する。

### 3.3. シークレットを混入させない
`*.tfvars` の実値・SA キー・`.env` は `.claude/settings.json` の `deny` で読み取り自体を禁止し、
`.gitignore` でコミットも防ぐ。二重に守る。

### 3.4. ドリフトさせない
ハーネスが指す前提（ディレクトリ構成・コマンド・コンポーネント名）を変えたら、
CLAUDE.md と本ファイルを同じ PR で更新する。`spec-guardian` サブエージェントで更新漏れを点検する。

### 3.5. 定型作業はコマンド化する
3 回以上繰り返す手順は `.claude/commands/` に切り出す。手順が口伝になる前にコマンドにする。

## 4. 標準ワークフロー（例）

```text
1. /issue-branch <番号>     … Issue とコメントから担当範囲を確認し、規約ブランチを作成
2. /spec                    … プロダクト概要・MVP 仕様で現在地を把握
3. 実装 / IaC 編集
4. /tf-plan                 … infra を fmt / validate / plan
5. iac-reviewer サブエージェント … Terraform 変更をレビュー
6. spec-guardian サブエージェント … 仕様整合・ドキュメント更新漏れを点検
7. PR 作成 → CI(plan) 確認 → レビュー → マージ → apply(CI)
```

## 5. 拡張の指針

- ハーネスは「育てる」もの。最初から完璧を目指さず、運用で詰まった点をコマンド／エージェント／
  規約に落とし込んで継続的に改善する。
- 追加・変更の判断基準は「**次に同じ作業をする人（人間/AI）が、この diff のおかげで迷わなくなるか**」。
